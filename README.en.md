# crypto-market-indicators

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

English | [简体中文](README.md)

Automated collection and maintenance of crypto market indicator data, plus a multi-factor quantitative strategy backtesting and visualization system. Currently supported:

- Coin Metrics: MVRV (`CapMVRVCur`) for BTC and ETH
- Binance Spot: daily OHLCV for BTC/USDT, ETH/USDT
- Binance Futures: perpetual funding rate for BTC/USDT, ETH/USDT
- Alternative.me: Crypto Fear & Greed Index

Collected data is stored as CSV files under `data/`, ready for market analysis, quantitative research, strategy backtesting, and visualization. The project can be run locally, or updated automatically every day via GitHub Actions.

## Features

### Data collection

| Dataset | Source | Assets / pairs | Frequency |
| --- | --- | --- | --- |
| MVRV | Coin Metrics Community API | BTC, ETH | 1 day |
| Spot OHLCV | Binance Spot API | BTCUSDT, ETHUSDT | 1 day |
| Funding Rate | Binance Futures API | BTCUSDT, ETHUSDT | 8 hours |
| Fear & Greed Index | Alternative.me API | Whole market | 1 day |

### Incremental updates

The script reads the last timestamp of each existing CSV and only requests newer data. After merging old and new data, it will:

1. sort by timestamp;
2. drop duplicate timestamps, keeping the latest record;
3. verify timestamp continuity;
4. check for missing or invalid values;
5. write the CSV only if the data actually changed.

If a gap, missing timestamp, or null value is detected, the script raises an exception and refuses to write, protecting existing data from corruption.
The Fear & Greed Index is the only dataset with a documented exception for known upstream historical gaps (see below); all other datasets are still subject to strict continuity checks.

For Binance data, requests prefer public market-data-only spot endpoints, with a bounded list of candidate endpoints, a limited retry count, and exponential backoff for both Spot and Futures. On HTTP 403/451-style access restrictions the script switches to the next candidate endpoint as quickly as possible; on HTTP 429, 5xx, timeouts, or connection errors it retries within the configured limit and logs diagnosable messages.

## Installation

### Requirements

- Python 3.10 or newer
- Network access to the Coin Metrics, Binance, and Alternative.me APIs

GitHub Actions runs on Python 3.12.

### Clone the project

```bash
git clone https://github.com/PXLabs-code/crypto-market-indicators.git
cd crypto-market-indicators
```

### Create a virtual environment

Linux/macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Windows PowerShell:

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
```

### Install dependencies

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Main dependencies currently in use:

- `pandas`: time-series processing and CSV I/O
- `requests`: calling third-party HTTP APIs

All APIs used are public; no API key or extra environment variables are required.

## Usage

### Update all data

```bash
python scripts/update_data.py
```

The script updates, in order:

- BTC MVRV, spot daily OHLCV, and funding rate
- ETH MVRV, spot daily OHLCV, and funding rate
- Fear & Greed Index

On first run it creates the `data/` directory; subsequent runs update the existing CSVs incrementally.

### Run tests

```bash
python -m unittest discover -s tests
```

Test coverage includes:

- daily time-series continuity
- gap detection in time series
- merging and deduplication of old/new data
- missing-value detection
- Binance endpoint failover, bounded retries, log truncation, and all-endpoints-failed handling

## Data directory and format

After a successful run, data is stored in the following layout:

```text
data/
├── btc/
│   ├── mvrv.csv
│   ├── spot_ohlcv.csv
│   └── funding_rates.csv
├── eth/
│   ├── mvrv.csv
│   ├── spot_ohlcv.csv
│   └── funding_rates.csv
└── market/
    └── fear_greed.csv
```

All `timestamp` fields use UTC and are exported in ISO 8601 format:

```text
YYYY-MM-DDTHH:MM:SSZ
```

### `data/{asset}/mvrv.csv`

MVRV data for BTC and ETH.

| Field | Type | Description |
| --- | --- | --- |
| `timestamp` | datetime | UTC data timestamp |
| `mvrv` | float | Coin Metrics `CapMVRVCur` indicator value |

Example:

```csv
timestamp,mvrv
2026-01-01T00:00:00Z,1.85
```

### `data/{asset}/spot_ohlcv.csv`

Binance spot 1-day candlestick data.

| Field | Type | Description |
| --- | --- | --- |
| `timestamp` | datetime | Candle open time (UTC) |
| `open` | float | Open price |
| `high` | float | High price |
| `low` | float | Low price |
| `close` | float | Close price |
| `volume` | float | Base asset volume |

Example:

```csv
timestamp,open,high,low,close,volume
2026-01-01T00:00:00Z,90000.0,92000.0,89000.0,91000.0,12345.67
```

### `data/{asset}/funding_rates.csv`

Binance USDⓈ-M perpetual futures funding rate data.
If the Binance funding-rate endpoint is temporarily unavailable or blocked by regional restrictions, the update script emits a non-fatal issue summary and a GitHub Actions warning annotation; it fails hard only when `FUNDING_FAILURE_POLICY=fail` is set.

| Field | Type | Description |
| --- | --- | --- |
| `timestamp` | datetime | Funding settlement time (UTC) |
| `funding_rate` | float | Funding rate as a decimal, e.g. `0.0001` means `0.01%` |

Example:

```csv
timestamp,funding_rate
2026-01-01T00:00:00Z,0.0001
```

### `data/market/fear_greed.csv`

Alternative.me Crypto Fear & Greed Index data.

The full upstream history has known missing days: `2018-04-14`, `2018-04-15`, `2018-04-16`, and `2024-10-26` (see this [public collection record](https://github.com/jungmin127/study/blob/f685267e772b6d95453b4dbbbd9632acc3079924/260711-upbit-v1/external_data_service.py#L26-L44) and an [independent record of the 2024-10-26 gap](https://github.com/cancleeric/trustforge/blob/6db496cc8b4b7fe2a5e09d8a003c715365441693/docs/qa/HERMES-FIVE-YEAR-BACKFILL-STARTED-2026-07-17.md#L5-L18)).
Validation only allows these specific dates to be missing, and logs a warning; it never interpolates, forward-fills, or fabricates data for them. If the upstream later backfills these dates, they merge in normally.
Any other missing day, abnormal timestamp, or null value still fails the update and preserves the existing CSV.

| Field | Type | Description |
| --- | --- | --- |
| `timestamp` | datetime | UTC data timestamp |
| `fear_greed_value` | integer | Index value, typically in the range 0-100 |
| `classification` | string | Market sentiment classification, e.g. `Extreme Fear`, `Fear`, `Neutral`, `Greed`, or `Extreme Greed` |

Example:

```csv
timestamp,fear_greed_value,classification
2026-01-01T00:00:00Z,65,Greed
```

## GitHub Actions: automated data updates

The workflow file is `.github/workflows/update_data.yml`, named **Update Market Data**.

### Schedule

The workflow uses the following cron configuration:

```yaml
schedule:
  - cron: '5 0 * * *'
```

It runs automatically every day at **00:05 UTC** (08:05 Beijing time). GitHub Actions scheduled runs may be delayed a few minutes due to platform load.

### Update flow

The workflow:

1. checks out the repository;
2. installs Python 3.12;
3. installs dependencies from `requirements.txt`;
4. runs `python scripts/update_data.py`;
5. checks whether `data/` changed;
6. if it changed, commits and pushes to the current branch automatically;
7. if it did not change, finishes normally without creating an empty commit.

The workflow currently uses `actions/checkout@v7` and `actions/setup-python@v7` for compatibility with Node.js 24 on GitHub-hosted runners.

The auto-commit message format is:

```text
Update market data: YYYY-MM-DD
```

### Manual trigger

The workflow is configured with `workflow_dispatch` and can be run manually from the GitHub UI:

1. open the repository's **Actions** tab;
2. select **Update Market Data**;
3. click **Run workflow**;
4. choose the target branch and confirm.

### Permissions

The workflow needs to push updates to the repository, so it is configured with:

```yaml
permissions:
  contents: write
```

If the workflow can collect data but fails to push, check:

1. repository **Settings → Actions → General → Workflow permissions**;
2. whether the workflow has `contents: write` permission;
3. whether default branch protection rules block direct pushes from GitHub Actions;
4. whether an organization-level Actions policy overrides the repository configuration.

If the default branch requires all changes to go through a Pull Request, adjust the workflow to create a branch and Pull Request instead of pushing directly.

## Adding a new asset

`update_asset()` takes a Coin Metrics asset code and a Binance trading pair. To add another asset, add a call in `main()`:

```python
update_asset("sol", "SOLUSDT")
```

Before adding an asset, confirm:

- the Coin Metrics Community API provides the `CapMVRVCur` indicator for it;
- both Binance Spot and USDⓈ-M Futures support the corresponding trading pair;
- the data frequency satisfies the current strict continuity validation rules.

## Multi-factor quantitative strategy backtest and visualization

Beyond data collection, this repository also ships a complete crypto multi-factor quantitative strategy backtesting system (`scripts/backtest.py`) that automatically generates an interactive HTML dashboard from the daily data in `data/`.

### Data preprocessing

- Funding rate is aggregated to a UTC daily mean (`groupby(date).mean()`).
- All datasets are left-outer-joined on `timestamp`, anchored to the BTC price date axis.
- Missing values are only handled with `.ffill()` (forward fill); `.bfill()` is never used, to avoid look-ahead bias.

### Strategies

The system uses the strategy pattern (`BaseStrategy` base class plus subclasses implementing `generate_signals(df)`). Every strategy's position is graded as `[0%, 25%, 50%, 75%, 100%]`, and the position generated on day T is always `shift(1)`-ed so it only takes effect on day T+1, avoiding look-ahead bias:

| Strategy | Description |
| --- | --- |
| a) Buy & Hold benchmark | 100% position throughout |
| b) Trend Following | MA20/MA200 crossover with graded deviation thresholds |
| c) Valuation Mean-Reversion | MVRV historical percentile buy-low/sell-high |
| d) Sentiment Regime | Fear & Greed Index extreme reversal |
| e) Multi-Factor Scoring | Composite score from MVRV (35%) + FGI (25%) + funding rate (20%) + MA trend (20%) |
| f) Dynamic Vol-Targeting | Composite score direction scaled inversely by realized volatility |
| g) Donchian Breakout | 20/55-day channel breakout (simplified turtle-trading rules) |
| h) Funding Rate Squeeze | Perpetual funding rate short-squeeze / long-liquidation reversal signal |

Each strategy explicitly declares its "trigger condition -> target position" table in a `RULES` class attribute, which is rendered in both the dashboard and the Markdown report.

### Performance metrics

Computed with 365-day annualization for crypto markets: cumulative return, annualized return, maximum drawdown (MDD), Sharpe ratio (risk-free rate 0%), Calmar ratio, win rate, profit-loss ratio, number of position changes, and final equity based on an assumed $100,000 initial capital. Every position change deducts a one-way 0.1% fee/slippage cost proportional to the absolute position change.

### Interactive dashboard

Running the script produces a self-contained Plotly HTML dashboard in `reports/`, named `backtest_dashboard_<UTC timestamp>.html`, containing:

1. BTC price on a log scale, with a dropdown menu to switch which strategy's buy/sell (position-change) markers are shown;
2. a comparison of each strategy's cumulative equity curve (log scale), with legend entries that can be clicked to manually show/hide individual strategies;
3. a comparison of each strategy's dynamic drawdown (%) fill chart;
4. a sortable strategy performance comparison table, plus the latest (T-0) position forecast signal for each strategy.

### Running locally

```bash
python -m pip install -r requirements.txt
python scripts/backtest.py
```

The generated dashboard is written to `reports/backtest_dashboard_<UTC timestamp>.html`.

### GitHub Actions: automated backtests

The workflow file is `.github/workflows/backtest.yml`, named **Strategy Backtest**:

- Triggers: `workflow_dispatch` (manual) and `workflow_run` (automatically, after **Update Market Data** completes successfully);
- runs the backtest script and appends the strategy performance Markdown comparison table to the Job Summary (`$GITHUB_STEP_SUMMARY`);
- commits the generated dashboard HTML back into the repository's `reports/` directory, and also packages it as a Workflow Artifact (`backtest-reports`) for download.

## Notes

- All timestamps are handled in UTC.
- Binance limits each request to 1000 records; the script automatically paginates in a loop to backfill history: Spot fetches 1000 records per batch and continues from the last candle's time + 1 day, Funding fetches 1000 records per batch and continues from the last `fundingTime` + 1ms.
- MVRV is fetched via Coin Metrics' `next_page_token`-based pagination until the full history is backfilled.
- The initial backfill uses an explicit historical start time rather than relying on the API's default "most recent data" behavior.
- If a third-party API is temporarily unavailable, rate-limited, or returns discontinuous data, the job fails and does not write anomalous results.
- Binance requests log the failed endpoint, status code, and a truncated response body; if all candidate endpoints fail, the script exits with a non-zero code to avoid writing incomplete data.
- If all of a GitHub-hosted runner's Binance candidate egress points are still affected by regional or compliance restrictions, consider using a self-hosted runner or integrating another compatible data source; fallback endpoints are not guaranteed to bypass these restrictions.
